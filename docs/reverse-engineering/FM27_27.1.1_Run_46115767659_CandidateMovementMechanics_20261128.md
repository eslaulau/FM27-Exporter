## 本轮结论

本轮已将 OOP 候选行为处理链从候选状态更新推进到空间候选处理，并反编译 Movement Director 的空间入口变换。确认引擎不是由单个 PI 开关直接决定一个跑位，而是把**比赛阶段、球员候选状态、位置/角度几何、对手空间关系、时序标量和战术状态**组合起来处理。

但目前还没有完整解出候选评分权重、所有状态位的语义、空间条目生成器，以及最终球员移动执行器。因此不能把本轮函数称为完整跑位公式。

### 0x4873400 — OOP 候选过滤

反编译确认它会：
- 使用 `MATCH_PLAYER+0x23E0` 候选资格状态、`+0x23D0/+0x23D1` 候选状态值；
- 按主客/队伍方向选择 `MATCH_PLAYER+0x1278` 或 `+0x1350` 的阶段 PI 记录；
- 检查上下文、球员关系、距离/空间条件和重复处理门控；
- 通过后调用 `0x4874AC0`，再进入 `0x496F840`。

### 0x4874AC0 — 阶段候选状态处理器

已确认的计算结构：
- 使用 `MATCH_PLAYER+0x23F0` 做当前处理/重入门控；另检查 `+0x23D4` 的状态位。
- 读取关联球员记录 `+0x2138`，比较双方位置坐标。
- 对坐标差按引擎 pitch 尺度常量缩放并量化，再通过表 `RVA 0x1858B6748` 查询角度索引。
- 角度索引按 `0x168`（360）循环比较，出现 `0x2D`、`0x3C`、`0x6F` 等门槛值（同一索引单位下的 45、60、111）。
- 同时检查球员、球、队友/对手、球门方向和阶段 PI 条件，生成多个候选状态位；随后调用个人指令/角色位置门控，包括 `0xA77D0`、`0xA7D20`、`0xA82F0`、`0xA79A0`、`0xA8080`。
- 不符合条件时会清除 `MATCH_PLAYER+0x23EF` 的候选/行为门控状态。

这表明 OOP 行为候选至少经过“状态门控 → 空间几何 → 阶段 PI → 角色/位置门控”多个阶段。未知状态位尚未映射到具体游戏 UI 行为，不能自行命名。

## 2. 0x496F840 — 候选空间仲裁 / 输出组织器

函数大小约 20,484 字节，本轮已成功反编译。

已确认：
- 从当前球员、比赛切片位置记录、球/阶段上下文和比赛状态取输入。
- 对候选方向使用 `0x1858B6748` 的空间角度查找表；以 360 单位为周期进行角度差和候选方向比较。
- 主体有一个方向候选遍历过程，循环上界为 `0x168`；过程中会结合候选状态、比赛阶段、目标点、球门/对手相对位置以及多个条件位筛选候选。
- 会调用 `0x4874AC0` 多次复核阶段候选状态。
- 计算/更新距离阈值字段 `param_5[0x21]`，并在末尾输出方向与状态信息。
- 最终会调用 `0x494F820` 做检查；该函数的准确条件尚待反编译。

本函数写入的输出包括：
- `param_5+0x2C`：短整数方向/角度索引；
- `param_5+0x1C`：64 位打包结果/标志；
- `param_5+0x2D = 0x55`：固定标记；
- `param_5+0x2F`：从球员记录复制的方向/侧别字段；
- 按检查结果可能设置 `param_5+0x71` 的 bit `0x04` 和 `param_5+0x72` 的 bit `0x10`。

**重要边界：**这证明了方向候选的几何处理和状态输出，不等于证明它就是最终跑动指令，也不代表所有候选都按一个单一分数排序。

### 字段归属更正（Run #59 复核）

上一轮的描述把第一个字段写成了 `MATCH_PLAYER+0x3C8`，这是将 Ghidra C 伪代码的数组下标误当成字节偏移。复核 `0x496F840` 的签名、`MATCH_PLAYER+0x2138` 关联指针、`+0x23D0/+0x23D1/+0x23DA` 等已确认球员状态字段后，确认 `param_1` 本身属于 MATCH_PLAYER 布局。因此：

- `param_1[0x3C8]` 是 QWORD 指针数组下标，换算为字节偏移为 `MATCH_PLAYER+0x1E40`；
- 另一个直接内存访问为 `MATCH_PLAYER+0x1E54`；
- 两个字段共同参与方向搜索步长选择。

字段语义及其生产者尚未映射。此前将其误归属到单独“仲裁上下文对象”的修正也作废；当前准确表述是 **MATCH_PLAYER+0x1E40 与 MATCH_PLAYER+0x1E54**。

### 方向搜索的自适应步长（新增细化）

在 `0x496F840` 的方向遍历循环中，确认了一个可量化机制：
- 方向以 `0x168`（360）为周期，循环起点来自当前参考角度；
- 初始化当前最优惩罚值为 `5000`，逐个候选角度计算复合惩罚，只有更优候选才替换当前方向；
- 搜索步长由 MATCH_PLAYER 的两个整数值（字节偏移 `+0x1E40` 与 `+0x1E54`）按阈值联合决定：
  - 两者均不低于 31：步长 5；
  - 否则两者均不低于 26：步长 8；
  - 均不低于 21：步长 10；
  - 均不低于 16：步长 12；
  - 均不低于 11：步长 15；
  - 均不低于 6：步长 18；
  - 任一低于 6：步长 20；若其中一个为 0，则步长 24。
- 每个候选方向会与多组参考角度进行 360 周期的最短角差比较，加入 45/60 等角度门槛以及额外参考方向的惩罚项，再与当前最优值比较。

**目前能证明的是：**方向搜索的采样分辨率会随两个球员状态数值字段而变化，候选方向由多角度条件共同选择。**目前不能证明的是：**这两个字段分别对应哪项属性/状态，以及惩罚项的所有系数和每个参考角度的战术含义。下一轮需要把这两个字段映射到其生产者和实际战术来源。


## 3. Movement Director：空间条目如何转换成目标点

### 0x4993230 — Movement Director 虚表第 7 槽

它不是完整移动算法，而是空间条目查找入口。其调用路径中会根据查询键找到一个空间条目，再调用 `0x492D060` 处理命中的条目。

### 0x492D060 — 空间条目入口变换

反编译大小约 2,873 字节。确认它处理 `0–9` 共十类条目，按 `param_7` 选取 Movement Director 内对应记录，条目中保存的坐标/端点数据会被读取；部分类型会对两个坐标分量取平均，类型 4 和 9 在新旧版本中有不同读取路径。

之后它：
1. 将条目目标与当前球员位置做三维位移计算；
2. 用平方和、平方根得到距离，并归一化方向向量；
3. 对类型 0–4，根据传入的限制参数及 `Movement Director+0xE38` 对投影距离进行限制，生成目标投影点；
4. 在较新版本（检查值大于 `0x1A08032C`）下，按球员索引从对方队伍的 11 个空间记录中寻找距离投影点最近的对象；
5. 检查最近对手的朝向/前向法线；必要时以对应球员的修正系数调整投影点；
6. 将结果交给 `0x492D840` 作进一步处理。

因此 `0x492D060` 是**候选空间条目的 opponent-aware 几何变换/投影层**。它会考虑最近对手距离与对手朝向，但不等于已解出整套移动决策。

## 4. 0x491FD30 — 被候选处理链调用的动态标量

该函数在本轮反编译中作为直接调用目标出现。其计算可以概括为：

- 从比赛当前 tick 与起始 tick 计算归一化经过时间，并限制在 0–1；
- 从球员记录及配置/provider 记录的多个字段组合一个球员相关基础值；
- 对特定状态（`MATCH_PLAYER+0x2CE == 4` 且 `+0x3C7 == 0`）加入由 `+0x3D7 % 11` 产生的小幅确定性变化；
- 通过 provider `+0x28` 设置下限；
- 再与 provider `+0x1C` 和另一归一化时间值组合，输出一个浮点标量。

源代码结构可表示为（常量与字段含义仍未恢复）：

```text
elapsedA = clamp((current_tick - start_tick) / C_A, 0, 1)
base = player_value
     + attribute_or_state_term
     + provider[0x34]
     - elapsedA
base = max(base, provider[0x28])

elapsedB = clamp((current_tick - start_tick) / C_B, 0, 1)
out = 0.5 * (base * W_A + (provider[0x1C] - elapsedB) * W_B + cached_base)
```

不能把它直接解释成“疲劳”“逼抢强度”或“速度”；在 provider 字段和调用上下文解明之前只称为动态标量。

### 7.1 `0x494F820`：候选运动样本的时序/轨迹检查

该函数体（2,815 bytes）已经成功反编译。它不是已证实的最终动作提交器。可确认的功能包括：
- 从模拟上下文的环形位置样本缓冲区读取历史/当前样本，必要时调用 `0x709800` 刷新样本；
- 使用候选记录中的时间/插值参数在两个位置样本间插值；
- 将候选位置与样本位置做坐标差、缩放和距离计算；
- 通过 `RVA 0x1858B6748` 的角度查找表计算候选方向，和上下文中的当前方向值比较；

这条路径表明候选移动会受到**时间样本、插值位置、方向一致性和距离容差**联合约束。目前仍未恢复全部样本字段、插值权重来源及不同调用场景含义。

### 7.3 OOP 评分器方法已确认挂接到同一 Provider

RTTI vtable 记录与初始化函数证明：
- `MATCH_OOP_SCORING_PROVIDER::OOP_ATTRIBUTE` 子对象 vtable `0x512E3C8`，slot 1 指向 `0x11FA50)；

### 8.6 `0x45AC0` 完整伪代码：方向搜索输入来自带种子的战术参数生成器

Run #3 热点反编译已拿到 `0x45AC0–0x498C0` 的完整伪代码（约 92 KB C 输出）。尽管 Ghidra loader 在函数表中只给入口建立了 1 字节占位，反编译器仍恢复出完整逻辑；Run #4 正在修正这一占位函数体长度，以恢复准确 CALL xref。

#### 已确认的状态生成方式

函数参数包含一个两 QWORD 的随机状态指针（`param_4`）。它反复执行：

```text
state = state * 0x5851F42D4C957F2D + increment
xorshifted = (old_state >> 45) XOR (old_state >> 27)
rotation = old_state >> 59
random32 = rotate_right(xorshifted, rotation)
```

这是一种 PCG 风格的 64-bit LCG + xorshift/rotate 输出结构。引擎不是每次从外部取得一个任意随机数，而是消费并更新传入的可复现随机状态。

#### `MATCH_PLAYER+0x1E40`

- 初始化值来自 `FUN_1848362D0(param_1, random_state, derived_bound)`；
- 其中边界由另一个 PRNG 输出及球员状态字段共同计算；
- 后续分支会再次调用 `FUN_1848362D0(..., -1)`，与已有值比较，并按情境取半值、较大值或较小值；
- 对某些指令码/阶段标志会再执行一次受约束的更新。

它不是一个静态属性字段，而是一个在球员参数生成/刷新过程中根据状态分支更新的派生数值。

#### `MATCH_PLAYER+0x1E54`

- 通过同一随机状态生成一个有界整数样本，计算形式为 `lower_bound + (random32 * range >> 32)`；
- 边界来自球员参数上下文中的 `+0x21F4` 等数值；
- 在特定状态分支中与另一个候选样本比较，并保留较大值，之后仍可能被候选行为条件再次调整。

因此 `+0x1E54` 也不是可以直接解释成“某个属性值”的原始字段，而是由种子随机数、状态边界和后续分支共同产生的模拟参数。

#### 生成器明确读取的战术/球员上下文

伪代码能直接看到以下读取和分支：
- `MATCH_PLAYER+0x1278` 与 `+0x1350` 两套阶段战术记录，按球队/阶段相关状态字段切换读取；
- `MATCH_PLAYER+0x23C7` 侧向标志、`+0x23E0` 行为门控、`+0x23F1` OOP 槽位；
- 球队上下文中的 `+0x154EC`、`+0x1556E`、`+0x15570`、`+0x15575` 扩展模式字段；
- 多组紧凑指令/状态码序列，依照当前阶段和候选门控选择分支。

**本轮可以确认：**两个方向搜索输入是“战术状态参与控制的派生模拟参数”，不是球员属性栏里某一个属性的简单映射。球员行为机制的链条现在已经连接为：

```text
阶段战术记录 / OOP 槽位 / 个人状态 / 球队扩展模式
                 ↓
0x45AC0：读取战术状态并消费 seeded PRNG
                 ↓
MATCH_PLAYER+0x1E40 / +0x1E54（及其邻接派生参数）
                 ↓
0x496F840：按两项参数选择方向搜索步长
                 ↓
角度候选与空间惩罚 → 候选方向输出
                 ↓
0x492D060：按目标点和最近对手位置/朝向修正空间目标
                 ↓
0x494F820：时间样本/插值/角度/距离容差验证
```

仍待确定：
1. `0x48362D0`、`0x49A20`、`0x49ED0`、`0x49B40` 各 helper 的返回值究竟对应什么基础分布/条件值；
2. 哪些 UI 级个人指令 ID 映射到生成器检查的紧凑指令码；

### 8.7 热点反编译器函数体修正

Run #3 已产出完整的 `0x45AC0` C 伪代码（约 92 KB），但其 Ghidra `Function.getBody()` 长度仍为 1 byte。根因是 PE loader 在入口先创建了占位函数；Decompiler 可以根据入口反编译出函数代码，但本项目原先按函数体枚举 CALL xref 时只能看到一个字节，造成 `DIRECT_CALLEES_ANALYZED=0`、`INCOMING_CALLERS_ANALYZED=0`。

Run #4 的脚本已改为：
1. 从 PE Exception Directory / `.pdata` 取得每个 RVA 的真实函数结束地址；
2. 对完整 `.pdata` 范围反汇编，合并已有与新生成的指令；
3. 将完整地址集合写回已有的入口占位函数（`Function.setBody`），只在无法扩展时再移除并重建；
4. 从扩展后的函数体统一枚举 CALL / incoming caller；
5. 将单轮 direct callee 上限提升到 96，确保本轮新增 Shot Zone 高频调用点得到覆盖。

这不是引擎逻辑变化，而是分析器的函数边界修复。后续只有在函数体范围与 CALL xref 都可核验时，才把“直接调用链已完整”标为确认。

#### `0x4943510`：射门区域候选的历史几何过滤器

### 10.2 `0x48334D0`：概率门控字段的状态依赖更新

### 10.3 `0x46E4740`：对 11 个槽位记录执行位掩码调节

此函数的第一个参数带有记录数组和长度/结束指针，另有随机状态和比赛/球队上下文。它目前只能被称作“槽位参数位掩码调节器”；没有足够证据将这些位直接命名成某项 PI/TI。它的调用者/数据生产者仍需确认。

### 10.4 `0x47E44C0`：必须区分 Shot Zone 专用路径

一个容易误判的点：该函数确实是 `MATCH_PLAYER` 辅助字段的写入者之一，但 Run #7 的直接 CALL xref 显示，`0x47E44C0` 由 `0x481A6A0` 调用（调用点 RVA `0x481DD9D`）。`0x481A6A0` 已确认为 Advanced Shot Zone 主处理器。因此 `0x47E44C0` 至少存在于 Shot Zone 计算/样本处理调用路径，不能仅因它写入方向分布辅助字段，就把它解释成所有球员日常跑位参数的通用装载器。

这一发现要求后续把“普通 MATCH_PLAYER 参数初始化”与“Shot Zone/射门空间处理过程中临时或专用更新”分开分析。它的完整伪代码也涉及大量向量/浮点临时值和阶段上下文；其输出字段 `+0x2214` 如何被消费，必须和 `0x48362D0` 的参数读取关系共同核验。

### 10.6 `0xF8050`：高优先级 MATCH_PLAYER 实例初始化路径

Run #7 对 `0xF8050` 的完整伪代码显示，它不只是某个分布字段的二级写入点。函数签名为 `FUN_1800F8050(longlong *player, ulonglong *seed, longlong team_context, char side, byte slot)`（参数名为分析者标注，类型/语义仍需以调用者确认），而其字段和对象关联强烈指向 MATCH_PLAYER 实例初始化：

- 将球队/比赛上下文指针保存到对象偏移 `+0x190`（即 qword index `0x50`）；
- 将当前对象注册到 team `+0x14ED8/+0x14EE0` 记录数组（计数最多 `0x34`）；
- 按 side/slot 从 team `+0x15380` 选择两套槽位记录，保存关联指针；
- 写入 `MATCH_PLAYER+0x23C7`（side 参数），并把槽位参数写入 `+0x23F1/+0x23F2`（小于 11 保留，否则为 -1）；
- 消费传入的 seeded PRNG 状态，生成并初始化多个数值字段，包括 `+0x219C`、`+0x22B4` 及对象中其他分布/状态字段；
- 根据比赛/球队和槽位上下文设置 `+0x23F3` 等状态码，末尾还会读取 `+0x2214` 派生另一个值写到对象 `+0x42D`。

因此，本函数是当前最接近“MATCH_PLAYER 对象创建/初始化时，比赛上下文和初始派生参数如何绑定”的入口。**尚未确认它的 C++ 类名、构造函数身份以及全部参数的真实调用约定**；需要 Run #8 的 incoming caller 及其调用点来验证。

这条发现将后续研究拆成两段：
1. `0xF8050`：对象建立时的初始上下文、槽位绑定和 seeded 参数；
2. `0x3C720`、`0x3BDB0`、`0x48334D0` 等：建立之后的基础字段/概率字段刷新和条件修正。

### 10.7 `0x3BDB0`：`+0x21F0` 并非简单复制的概率修正量

`0x3BDB0`（2,393 bytes）首先执行 `MATCH_PLAYER+0x21F0 = MATCH_PLAYER+0x2230`，随后按多个比赛状态条件调整：

- 双方的时间/阶段数据（包括上下文对象的 `+0x122`、`+0x72A)、`+0x131`）；
