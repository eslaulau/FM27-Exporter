## 3. Movement Director 空间映射层

Run #56 将 `MATCH_MOVEMENT_DIRECTOR` vtable 15 个槽位全部加入分析。slot 7 的 RVA `0x4993230`，函数体 263 bytes：

- 对输入 32-bit key 执行 FNV-1a 风格哈希（basis `0xcbf29ce484222325`，multiplier `0x100000001b3`）。
- 使用按侧向/索引分组的 bucket mask 与桶头执行链式查找。
- 比较条目 key；条目类型 byte 位于 `entry+0x14`。
- 类型不是 10 时调用 `0x492D060`；否则或未命中时复制 fallback coordinate record。

`0x492D060`（函数体 2,873 bytes）：
- 根据类型 `0–9` 选择 Movement Director 内部几何/锚点子记录；按 side 使用 `0x168` stride 读取数值对并生成坐标。
- 类型 4 和 9 包含版本门控路径（版本字段与 `0x1A080328` 比较）。
- 以输入点为基准计算并归一化空间向量，结合距离参数与 Director `+0xE38` 扩展值形成投影目标，再调用 `0x492D840` 后处理。
- 在版本高于 `0x1A08032C` 的路径中，扫描对方 11 个位置槽（stride `0x34`）寻找近邻对手；使用对手朝向向量 `+0xA0/+0xA4` 和对应参数调整投影点。

**严格结论：**这是由哈希映射条目选择类型、再执行几何投影和近邻对手修正的空间变换路径。类型 0–9 的 UI/战术语义尚未映射，不能把它们直接命名为某个角色或跑位指令。

## 7. Run #9：0x47E44C0 是 match-tick 中的方向/轨迹空间行为计算器

Movement Handoff Run #9 的直接反编译补充了一个重要的下游行为计算函数：`0x47E44C0`，body 6,058 bytes；它由 `0x51820` 直接调用（CALL site `0x51F6F`）。该函数的参数布局显示第一个参数是 MATCH_PLAYER 相关对象：`param_1[0x1c6][4]` 对应 player `+0x1C64` 状态字节；经 `param_1[0x28]` 访问 match context / tick。

### 已确认的计算步骤

1. **状态与时间门控**
   - 读取 player `+0x1C64`、`+0x1C6C`，结合角色/槽位类状态 byte、match tick `+0x154EC` 以及多个 phase/timing window。
   - 不满足状态/时间条件时直接清理或跳过部分候选计算。

2. **候选位置取样**
   - 在多个分支调用 `0x47F1E70`，以 player、match time/phase context 和输出缓冲区为输入，取得指定时间样本的二维位置与辅助状态。
   - 将该样本位置与 player 当前 XY `+0x140/+0x144` 比较，计算欧氏距离。

3. **方向量化与角度容差**
   - 对二维位置差按常量比例缩放，超出范围时通过右移归一化，再查询方向表 `0x1858B6748`。
   - 同一球员的当前/目标方向索引计算 wrapped delta：先取绝对差，再与 `360-delta` 比较取较小值。
   - 当最小角度差小于 `0x5B`（91 个方向单位）时，进入后续方向偏移/空间点计算；这不是任意方向都放行的无条件移动。

4. **距离驱动的偏移向量**
   - 以方向索引访问 `0x185890D98` 的向量/距离表；当索引未超过 99 时读取对应样本，否则使用表项 `+0xA0/+0xA4` 的 fallback 系数。
   - 将计算出来的二维偏移加到候选位置，生成新的空间点，再进入对手空间检查。

5. **对手轨迹/空间冲突检查**
   - 遍历对方球队位置槽（容器起点 `+0x388`，数量字段 `+0x730`）。
   - 结合对方 player 的状态 `+0x1C64/+0x1C6C`、时间字段和有效性门控过滤对象。
   - 对对方球员调用 `0x47F1E70`、`0x48A6E20` 取得预测位置/相关值，并计算与前述候选空间点的间距；不满足距离/时间条件则跳过该对象或分支。
   - 因此它至少包含“候选方向/目标点生成 + 与对手预测位置的时空冲突筛选”两层计算。

### 证据边界

已确认这不是单纯参数复制或 UI 指令加载函数，而是由 match tick 后处理调用的 per-player 方向/空间候选计算。尚未确认：
- 每个 state/role byte 的完整中文 UI 名称；
- `0x47F1E70` 采样结果的完整字段定义；
- `0x47E44C0` 的最终输出具体由哪个结构接收、是否直接提交 Transform；
- 这些分支是否逐一对应某个 PI / duty 或 movement director 类型。

它与 Movement Director `0x492D060` 是两条已知空间计算路径；目前不能将它们混为同一个函数，也不能假设它们对所有球员/阶段都同时执行。

## 8. Run #7：0x2AFB290 位置应用分支的更准确边界

Record Run #7 的伪代码再次核实：
- `0x2AFB290` 遍历 match/team player pointer 数组。
- 对 `MATCH_PLAYER+0x23C6 == 1` 的分支，它初始化/刷新方向和运动候选记录（使用 `0x1858B6748` 方向查表，以及 `0x4709800` / `0x4707AA0` 历史/空间处理）。
- 对另一个状态分支（`(byte)(MATCH_PLAYER+0x1233) > 0x84`），若 player 时间 `+0x208` 满足 `-1 < time < match tick`，则执行：
  `player+0x140..+0x147 = player+0x150..+0x157`；
  `player+0x148..+0x14F` 相关缓存也同步到活动位置区。
- 它同时写入 `+0x1BB0/+0x1BC0` movement record 和 `+0x1C64/+0x1C6C/+0x1C70` 状态字段。

因此准确名称应是**按 player 状态/时间门控执行的运动记录更新与缓存位置应用器**。这比“所有候选被接受后立即写 Transform”更窄。与 `0x61660` handoff 的直接调用链仍需通过它的两个 callers `0x42D3910`、`0x42D58E0` 验证。
