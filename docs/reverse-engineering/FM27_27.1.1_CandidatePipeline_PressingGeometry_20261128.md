# FM27 27.1.1 — Native Candidate Pipeline and Pressing Geometry Notes

**Build target:** FM27 27.1.1+2511875  
**Binary:** `fm_Data/Plugins/x86_64/game_plugin.dll`  
**Image base:** `0x180000000`  
**Status:** static reverse-engineering findings; not yet a validated tactical recipe.

## Why this pass matters

The prior pass established that role/PI records do not directly become movement orders. The engine has a candidate-generation stage, phase/role/PI filters, and separate pressing-geometry routines. This note records the additional relationships that can now be followed rather than treating role IDs or PI flags as isolated labels.

## 1. Tracking Centre Forward is a real OOP candidate generator

Native RVA `0xA7280`, previously named `TRACKING_CENTRE_FORWARD_CANDIDATE_BUILDER`, is called by `0x4862CB0` (call site `0x48631D5`).

The builder:
- Selects the active IP/OOP PI record from `MATCH_PLAYER+0x1278` or `+0x1350`, based on the match-side/phase selector.
- Requires the relevant low PI bit and rejects a specific context flag on its input.
- Requires tactical phase/mode byte `+0x1556A == 4`.
- Checks whether the player is the phase-selected target, then evaluates the player's position relative to the tactical/ball reference.
- Applies additional match-time, position, and event-window gates before emitting a candidate.
- Writes candidate position coordinates, a distance/weight at candidate record `+0x84`, flag `0x20000000` at `+0x70`, and OOP compact role ID `0x58` at `+0xB4`.

The OOP compact role map independently resolves `0x58` to Tracking Centre Forward. This is stronger than a UI role label: the function creates a role-specific spatial candidate with a measurable distance field.

**Interpretation limit:** the builder proves candidate creation and gating, not that this candidate always wins arbitration or causes a particular run in a match.

## 2. The phase processor is an arbitration/gating layer, not a generic player update

Native RVA `0x4874AC0` is called by the larger OOP candidate path `0x4873400`. It is also the direct consumer of:
- `0xA77D0` — PI state filter / behavior gate;
- `0xA8080` — PI trigger, phase and target gate;
- `0xA82F0` — role/duty/PI/position gate.

The processor:
- Uses `MATCH_PLAYER+0x23F0` as a re-entry/processing guard.
- Reads both phase PI records (`+0x1278/+0x1350`) and candidate state bytes (`+0x23D0/+0x23D1`, `+0x23E0), plus `+0x23EF` and OOP slot `+0x23F1` in the surrounding caller path.
- Calculates relative player/ball/opponent geometry and quantized directional/angle information.
- Has version-gated branches and role/phase-specific checks; it is not a single universal “press more” switch.
- Returns a Boolean gate to `0x4873400`; the caller then either rejects the candidate or calls `0x96F840` and returns success.

The surrounding `0x4873400` path also applies team-side, spatial, time-slice and candidate-state filters. It clears `MATCH_PLAYER+0x23EF` on rejection paths. This reinforces that `+0x23EF` is a mutable behavior/candidate gate, while `+0x23E0` is a separate eligibility/state byte.

## 3. Pressing manager implementations are spatial geometry providers

The three RTTI-resolved implementations are:
- `0x47FA990` — implementation A;
- `0x4996D50` — implementation B;
- `0x4997910` — implementation C.

They are not just reading a team “pressing intensity” scalar. Their decompilations consume match-slice positions, player/ball coordinates, phase PI records, side orientation and tactical state, and write spatial outputs.

### A — zone / lane classification

Implementation A normalizes the player's location using pitch dimensions and offsets, quantizes it into a coarse grid, and transforms the cell index according to side orientation. Several grid-cell classes branch into opponent scans. Those scans filter by the opponent's active phase PI flags and compare squared spatial distances. It therefore combines pitch-zone classification with the presence/location of phase-qualified opponents.

### B — opponent-relative interception / shadow geometry

Implementation B examines the player's side of the ball and scans opponents in a directional half-space. It chooses a nearest qualifying opponent, then derives a normalized direction and projects a point onto the line between the ball/reference point and that opponent. It writes the resulting 4D spatial vector through its output pointer. This is evidence of geometric pressing/cover-shadow support, not merely a press-frequency setting.

### C — tactical-mode dependent target point

Implementation C first branches on a tactical state word at `param_3+0x298` offset `0x18D0` (bits `0x4` and `0x20`). Depending on the active mode and whether a ball-carrier/related player pointer exists, it:
- returns a midpoint between two match-state positions;
- selects the nearest opponent matching role/PI masks (including `0x2480` and `0x6490` paths);
- or computes a point along the ball-to-player vector and writes it as a spatial target.

The exact semantics of the state bits and the output consumers still need to be mapped before assigning user-facing instruction names.

## 4. What this changes for the four-defender project

The engine's defensive behavior needs to be analyzed as a pipeline:

`formation / IP-OOP role + duty + PI`
→ `phase-specific PI record`
→ `candidate eligibility and behavior gate`
→ `spatial candidate generation / arbitration`
→ `pressing geometry providers`
→ `movement/action consumer`

Consequences:
- Do not assume that a defender's OOP role alone determines whether they press, cover, or track. The active phase record, state bytes and spatial geometry all participate.
- Do not treat a high press line or Trigger Press PI as a direct movement command. They feed a more conditional system.
- For a four-back IP shape, the next useful question is whether the four fixed back-line slots remain eligible for the same candidate families when the OOP role/PI records change, and whether pressing geometry pulls one of them out of the line.
- Candidate distances and final target vectors should be captured alongside match outcomes; the existence of a candidate is not proof of a successful press or run.
