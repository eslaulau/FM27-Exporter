## 1. XG_SHOT_DATA event writer：0x4C01760

`0x4C01760` 的函数体 788 bytes。其入口参数包含 match、event/context、team/player references，以及一个 event 分支 flag。

在 `param_6 == 0` 分支：

1. 读取 match `+0x148B0`，把该整数累加到：
   - 当前 team object `+0x288+0x70C`；
   - player `+0x21C4`。
2. 调用 `0x498D400` 获取一个 32-bit 值；随后再次调用相同 target，返回值用于：
   `0x166400(param_4, value, -side, 0)`。
3. 设置 player `+0x23D4 |= 8`，并更新 match event/player association context。
4. 调用 `0x4D1F0` 构建/标记 shot event context。
5. 调用 `0x164680`，根据球的二维位置对 shot/goalkeeper 目标区域设置 bit flags。
6. 最终调用 `0x1691C0` 创建/去重 shot event payload，并发出匹配的事件通知。

### 证据边界

这段函数是**射门事件与统计登记路径**。它确实把 `0x498D400` 返回的数值交给 team stat/event queue，但目前还没有 `0x498D400` 的函数体，因此不能称此值为 xG，也不能声称 `0x4C01760` 自己执行了射门成功概率计算。

## 2. Supporting functions：都属于上下文/记账，不是已证实的 xG 公式

### 0x166400 — compact stat/event queue writer

函数体 133 bytes。把 `(value, side, category/flag)` 封装成短记录，追加到 `param_1+0x4C8..+0x4D8` 管理的缓冲区；容量检查为 400 bytes。它不计算 value。

### 0x4D1F0 — shot event context lookup / flag setter

函数体 645 bytes：
- 调用 `0x4D480` 取得上下文记录容器；
- 在已排序记录中按整数 key 进行二分/区间查找；
- 对命中条目修改 `record+0x64` bit flags；
- 依据调用方的状态位设置另一标志 `record+0x65 |= 2`；
- 之后释放/回收临时容器引用。

这里是上下文记录选择和标志写入，不是数值概率公式。

### 0x164680 — geometric shot/goalkeeper target-region classifier

函数体 494 bytes。读取球的 `x/y`，与内部球门/区域边界参数比较，并根据左右侧向与目标方向，在输出 64-bit mask 中置位（包含多个不同区域标志）。这证明事件系统会记录射门落点/目标位置所处的几何区域；没有看到它计算射门得分概率。

### 0x1691C0 — shot event payload finalizer

函数体 1,019 bytes：
- 根据 side、区域分类 byte、时间 key、player/stat key 等查找既有 payload，进行去重；
- 分配/初始化 compact payload，填入时间、球员、侧向、区域标记和相关 metadata；
- 将 payload 加入事件 buffer；
- 对若干事件类别通过对象 vtable slot `+0x38` 发出通知。

它构建和登记事件 payload，不是射门轨迹/门将扑救成功概率公式。

## 3. 0x481A6A0 — Advanced Shot Zone main processor 与球员空间行为的关系

函数体 21,842 bytes。尽管 RTTI/脚本 seed 以 Shot Zone 命名，伪代码显示它还涉及一条 per-player candidate / movement-record 计算路径：

- 迭代时间采样与球员/球队状态；
- 多处调用 `0x4800C40`、`0x4943510`、`0x4709800`、`0x48A6E20` 等状态/历史空间 helper；
- 调用 `0x47E44C0` 执行方向和对手预测位置冲突计算；
- 写入球员 `+0x1BB0..+0x1C65` 周围的候选/运动记录；
- 调用 `0x4D1F0` 给 event/context 记录设置标志。

因此它是 **shot-zone-associated spatial / player candidate processor**，与本项目的球员空间行为研究相连；不能因函数名含 shot-zone 就把它认作 xG 概率公式。

## 7. Important correction from full producer bodies: ball-kick event vtable method is a release callback

Run #1 also decompiled `0x42D2440`, the only virtual slot listed for `simatch::UBALL_KICK_SAMPLE_DATA::EVENT_T` at vtable `0x5205250`.

Its body (255 bytes) performs thread-local allocator/pool cleanup:
- pushes a released pointer into an interlocked SList;
- decrements a refcount/queue counter;
- conditionally calls a cleanup helper;
- otherwise frees the allocation.

It is therefore an **event object release/destructor callback**, not a ball-flight calculation or kick result handler. The previous seed label `BALL_KICK_SAMPLE_EVENT_HANDLER` was inaccurate and has been corrected in the analysis script/workflow.

The vtable itself has only one method in the RTTI table; its constructor/vtable address is referenced from `0x3E4E0`, `0x19EDD0`, and `0x5DBD0`. These are the real producer-side functions to inspect, rather than treating `0x42D2440` as physics.

## 8. 0x5DBD0 match tick invokes both trajectory sample building and directional-space prediction

The same `0x5DBD0` match-candidate tick dispatcher directly calls:

- `0x19EDD0` at sites `0x5E628) and `0x5FDCA`.

This is important because the two functions are not isolated from the match loop. They are called from the same match tick that also invokes candidate handoff `0x61660`.

### 8.1 0x3E4E0 — time-indexed trajectory/sample state builder

Confirmed from its 5,001-byte body:
- Reads match tick `MATCH+0x154EC) and match sample/event subscription list `MATCH+0x15588).
- When a subscriber has flag `0x80), emits a `UBALL_KICK_SAMPLE_DATA::EVENT_T` event through `0x42D5DF0), event vtable `0x5205250`, and includes a time/value payload from its input.
- Maintains a per-sample time window and bounded ring/buffer records; advances history using `0x47BA760).
- Computes 2D displacement from a target/sample point, normalizes large deltas, and quantizes direction through table `0x1858B6748).
- Applies pitch/boundary conditions and writes time-indexed position/direction/auxiliary values into internal records around `+0x6C0..+0x6F4).
- Multiple callers use it as a common sample update primitive, including `0x19EDD0), `0x5DBD0), and `0x47E44C0).

**Interpretation:** this is a match-time trajectory/sample state builder with a conditional ball-kick sample event side effect. The event name alone does not make the entire function a ball-flight solver.

### 8.2 0x19EDD0 — per-player directional-space predictor / candidate point generator

Confirmed from its 3,938-byte body:
- Reads the match context `param_1), current tick `+0x154EC), the player-side object `MATCH_PLAYER+0x140/+0x144), and a target/reference point from its input context.
- Reuses/caches a direction index based on the player-to-target XY delta through lookup table `0x1858B6748).
- Reads match/player timing and phase state, and branches on whether the player, target and current sample have changed enough to require recomputation.
- Uses a deterministic LCG-like state update (`state * 0x5851F42D4C957F2D + increment)) to derive a directional/angle adjustment; combines this with the quantized player-to-target direction.
- Uses the direction/radial lookup table `0x185890D98` to obtain distance-dependent 2D/auxiliary offsets, then adds them to the candidate point.
- Checks pitch boundaries and competing player/reference locations; on the conflict path calls `0x4707560` / `0x4707690` with player and target contexts.
- Writes time/state/position metadata into the per-player sample/decision buffer, and conditionally calls `0x3E4E0` to update the trajectory sample sequence.

**Interpretation:** this is a concrete player spatial behavior calculation: player/target geometry → quantized direction → deterministic angular perturbation → distance-scaled vector lookup → candidate point → boundary/conflict checks. It is not an xG formula.

### 8.3 Updated match tick structure

The confirmed `0x5DBD0` call graph now contains three coordinated mechanisms:

0x5DBD0 match-candidate tick

This is a shared match-tick orchestration relationship, not yet proof that every output is written into the same player record or consumed in the same state branch. Continue tracing shared player pointer, tick/sample index, and state fields to prove the exact join.
