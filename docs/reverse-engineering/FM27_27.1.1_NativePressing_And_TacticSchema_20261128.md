## 3. Match plug-in interop boundary

The managed metadata exposes two important interfaces in \`SI.Match\`:

- \`IPluginMatchInterface\`: Setup, entity/stadium/ball data, match info, entity snapshots, playback-interface retrieval and simulation period.
- \`IPluginMatchPlaybackInterface\`: Tick, time-slice state, ball/entity transforms, match-event updates, seek and playback control.

\`MatchState\` contains flags, time-slice, time, score and clock fields. This is an interop/playback boundary. The \`FM.Match.Simulation.Match2DSimulation\` class is the 2D presentation/update layer; it should not be mistaken for the native decision engine.

### Evidence observed in the decompilations

**Defender implementation candidate (\`0x1847FA990\`)**

- Reads a position/time-slice snapshot and pitch dimension fields.
- Clamps and normalizes X/Y coordinates against pitch dimensions.
- Quantizes the coordinates into a 3×3 sector index (the decompiled expression is row × 3 + column).
- Mirrors the sector index based on a side/orientation flag.
- Applies several sector bitmasks and player-state masks to select a branch.

This is evidence of spatial-sector classification. The exact meaning of each sector mask is not yet named.

**Midfielder implementation candidate (\`0x184996D50\`)**

- Iterates the team's player-pointer array at manager offset \`+0x260\`, with an 8-byte stride and a count at \`+0x71C\`.
- Excludes the current player and filters candidates through a status mask (including \`0x2480\`).
- Reads player coordinate fields around \`+0x140\` through \`+0x14C\`, computes squared distances, and selects a nearest eligible candidate in one branch.
- Compares candidate/current positions with an input target vector, normalizes a direction vector, and adjusts the output target according to a distance threshold.
- Other branches use 3×3 sector bitmasks (\`0x92\`, \`0x124\`), player-state masks (\`0x80\`, \`0x60\`, \`0x6490\`), and a forward-direction dot-product test when scanning other players.

This shows that the selected routine is spatial and state-dependent. The status masks, coordinate-field meanings, and global distance thresholds still need symbol/data cross-references.

**Attacker implementation candidate (\`0x184997910\`)**

- Branches on state bits from a structure at \`player + 0x298 + 0x18D0\`.
- In one branch, combines the positions of two referenced entities using constant multipliers.
- In other branches, scans the same team player array, excludes the current player, filters candidates by status masks, and selects a nearest teammate using squared X/Y distance.
- Another branch derives a normalized vector from the current player toward a time-slice/ball-related point.

This is evidence of branch-specific target-position selection, not yet a proven “pressing score” formula.

**Helper \`0x184996A50\`**

This helper reads the current/interpolated time-slice position from the match snapshot and copies its coordinate vector to the caller. The second helper \`0x184998130\` is a stack-cookie failure path (security check / fail-fast), not a tactical calculation.

## 5. What is and is not proven

### Proven in this batch

1. The exact seven-file v2 package was integrity-checked and all expected files were present.
2. Unity 6 metadata v39 was decoded successfully, with 20,104 types and the native method-address map generated.
3. The managed tactic schema exposes phase-specific team instructions, IP/OOP role IDs, role-associated PI metadata and explicit instruction groupings.
4. Three pressing-manager virtual-entry candidates have real decoded function bodies and decompilations, with two directly called helper routines identified.
5. At least these pressing-manager paths use spatial sectoring, candidate-player filtering, distance calculations and output target-vector adjustment.

### Not yet proven

1. The precise semantic names of the player status masks and native object fields.
2. The actual values and units represented by the distance thresholds and pitch constants.
3. Whether these three methods are the complete press-target selection path or only one stage in a larger scoring/decision pipeline.
4. How player attributes (Acceleration, Anticipation, Decisions, Work Rate, etc.) enter these routines or their callers.
5. The native weight/scoring formulas for \`MATCH_WEIGHTS_PROVIDER\` and \`MATCH_OOP_SCORING_PROVIDER\`.
6. Any causal gain in goals, xG, conceded shots or points from a particular role, PI or TI.

## 10. Live OOP position / role change propagation into MATCH_PLAYER

The unified native call-trace pass exposed a concrete live tactical update chain. This is a stronger link than the earlier tactic serialization methods.

### OOP position change handler

\`TACTICS_CREATOR_OOP_POSITION_CHANGE_SLOT_3\` at RVA \`0x42F59F0\` has the following observable behavior:

1. Reads the team index from the change record and obtains that team's live match/tactical state.
2. Reads the incoming OOP position identifier from the change payload.
3. Compares it with the team's stored OOP position-ID mapping at offsets \`+0x1FBC\` through \`+0x1FC6\`; it resolves the incoming ID to a normalized slot index in the range 0–10. If the payload uses the no-position sentinel (\`-1\`), that branch exits the remapping path.
4. Iterates the team's player objects and finds the player whose field at \`MATCH_PLAYER + 0x23F1\` equals the resolved slot.
5. Calls the team-record updater at RVA \`0x270BBD0\`, then copies the slot's tactical data into the selected player through RVA \`0x103A10\`, and calls the player refresh routine at RVA \`0x72B20\`.
6. Writes the team's current tactical revision/state field at \`team_state + 0x34C4\`.

This is direct evidence that an OOP position change does not remain only in the tactic editor: it is resolved to a team slot, applied to the corresponding live match-player object, and followed by a player refresh.

### Team slot record updater

\`0x270BBD0\` checks the slot index is below 11, then updates a slot-specific record at:

\`team_object + 9 * slot + 0x575\`

It copies multiple subordinate arrays/fields from the supplied record and then refreshes a pair of team-owned collections. The exact field labels are not yet recovered, but the 11-entry limit and the call site establish that this is the team-side OOP-position record store.

### Tactical snapshot -> MATCH_PLAYER copy

\`0x103A10\` copies a substantial tactical-data record into the live player object. Observed destinations include:

- player offsets \`+0x12C0\`, \`+0x12C8\`, \`+0x12E0\`, \`+0x12E8\`, \`+0x12F0\`, \`+0x12F8\`;
- mirrored/derived copies around \`+0x1278\`, \`+0x1280\`, \`+0x1298\`, \`+0x12A0\`, \`+0x12A8\`, \`+0x12B0\`;
- tactical bitfield from the source record's eighth 64-bit field, stored at \`+0x1300\) and mirrored at \`+0x12B8\`;
- derived internal state fields at \`+0x22D8\` and \`+0x22DC\`, computed from masks on that 64-bit field and a player state byte around \`+0x1925\`;
- further record copies beginning around \`+0x1398\).

The function is a live player-state/tactical snapshot application routine, not merely a UI serializer. The masks and derived numeric states remain unnamed; the next step is to trace the source-record constructor and consumers of \`+0x22D8/+0x22DC\`.

### Per-player tactical refresh

\`0x72B20\` reads the player's slot index at \`MATCH_PLAYER + 0x23F1\), then uses that index to retrieve the slot's team tactical record at:

- \`team_state + 0x1938 + slot * 0x48\`;
- a remapped/alternate slot record at \`team_state + 0x1C58 + mapped_slot * 0x48\`;
- for one branch, an extended record at \`team_state + 0x1978 + slot * 0x48\).

It writes selected fields back into the player around \`+0x12C0\), \`+0x1278\), \`+0x1398\), \`+0x1350\), and the extended state at \`+0x1300\)/\`+0x12B8\). The alternate path is conditioned on a team state bit; otherwise the remapped record is chosen using the team's OOP slot map at \`+0x1FBC\).

This provides a concrete structural path from OOP tactical slot assignment to the live \`MATCH_PLAYER\` runtime object. It does not yet prove which player decision/positioning equations consume each copied field.

### Role change handler

\`TACTIC_ROLES_CHANGE_SLOT_3\` at RVA \`0x42F8A40\` also applies a role-map change to live team state:

- resolves the team record using the team index in the change payload;
- when the role-map version/index differs, it invokes the team-role map copy at RVA \`0x1028A40\` into the live match/team structure at \`+0x6F0\);
- updates team/player role-selection indices by matching player identity references;
- under live-match conditions, it scans current player objects and may invoke an additional player/match-state update at RVA \`0x4BF67E0\`.

The helper at \`0x1028A40\` is primarily a deep copy of 8 groups of vector/array-backed role data, not the role-selection score itself. The live handler and the player update caller are the relevant behavior path.

### What this adds to the project

We now have a verified structural path:

\`OOP slot-change payload → team OOP slot mapping → MATCH_PLAYER slot match → tactical data copy → per-player tactical refresh\`

This allows later experiments to distinguish:
- changing a player's OOP slot assignment;
- changing the underlying OOP slot's tactical instructions/data;
- changing the role mapping for a player;
- changes to other PI/TI options.

The next pass traces the copied player's derived state fields (\`+0x22D8\`, \`+0x22DC\`) and reads/writes of the per-slot data arrays. No match-performance gain is claimed from this static mapping alone.


## 11. OOP slot record layout and MATCH_PLAYER tactical-state refresh

The newly seeded decompilations of \`0x270BBD0\`, \`0x103A10\`, and \`0x72B20\` allow the OOP update chain to be described more precisely.

### Eleven OOP slot records

The team record updater checks \`slot < 11\`, then addresses the selected slot as:

\`team_object + 0x575 + slot * 9 qwords\`

The stride is \`9 * 8 = 0x48\` bytes. It copies:
- a first pointer/range pair (the helper computes element count from an 8-byte stride);
- a one-byte property stored at the fifth qword's first byte;
- a second pointer/range pair (the helper computes element count from a 16-byte stride);
- the ninth qword.

After the copy it refreshes team-owned collections at \`team + 0x304\` and \`team + 0x4EE\`; a changed collection can trigger the team's virtual method at vtable offset \`+0x28\` and a further synchronization helper. This establishes an 11-entry per-position tactical record array, with variable-length sub-arrays and a one-byte option field.

### Per-player slot resolution and refresh branches

The player slot byte is read from \`MATCH_PLAYER + 0x23F1\`. It is used as an index into the team's 11 records:

- primary slot record: \`team + 0x1938 + slot * 0x48\`;
- extended slot record: \`team + 0x1978 + slot * 0x48\`;
- remapping array: \`team + 0x1FBC + slot\`;
- remapped slot record: \`team + 0x1C58 + mapped_slot * 0x48\`;
- remapped extended record: \`team + 0x1C98 + mapped_slot * 0x48\`.

The selected branch depends on a team-level flag byte around \`team + 0x1556E\`, with an associated selector byte at \`team + 0x15575\`. In the ordinary branch, the function reads the primary record and remapped record. In the extended branch, it also copies the extended record into the player's tactical bitfield at \`+0x1300\) and mirror \`+0x12B8\), plus the extended remapped record into \`+0x13D8/+0x1390\).

The refresh also:
- derives a byte at player \`+0x23CD\` from the slot record via \`FUN_18492ED70\`;
- examines both the primary and extended records via \`FUN_18484EDB0\` and conditionally stores a field at player \`+0x23A0\`;
- copies a per-slot team field from \`team + 0x1820 + slot * 0x10\` into player \`+0x16E0\`;
- invokes \`FUN_1800C5580(player)\` after refreshing the selected data;
- can update a reverse lookup from team \`+0x15340 + player_index * 8\` to the current player object.

### Derived player states

The snapshot copier \`0x103A10\` stores the primary instruction/role-like flag word at \`MATCH_PLAYER + 0x1300\` and mirrors it at \`+0x12B8\). It derives compact values:
- \`+0x22D8 = FUN_180104760(flags & 0x3FB7B49A90FDEFF)\`;
- \`+0x22DC\` is a branch-derived state. One branch computes \`FUN_180104760(flags & 0x06E00000)\`; another chooses constants \`0x5F\`, \`0x5B\`, \`0x5E\` or a related value after testing bits \`0x00800000\), \`0x06200000\) and the player-state byte at \`player + 0x298 + 0x1925\`.
- a secondary bitfield copied to \`+0x1390\) is reduced through \`FUN_1801043B0\` with masks \`0x3FFBF81FFFFF\` and \`0x406E00000\`, producing \`+0x22E0\) and \`+0x22E4\`.

The decompiler still does not give semantic names for these masks or state codes. However, these fields now provide high-value anchors for the next consumer search: functions reading \`MATCH_PLAYER + 0x23F1\`, \`+0x1300/+0x12B8\`, \`+0x22D8/+0x22DC\), \`+0x1390\), or \`+0x22E0/+0x22E4\).
